# 一次一个功能的开发顺序

基线：2026-10-28。F001～F006的基础范围已具备，先复用，不重新搭入口、框架、Prefab和题库。下表将其视为可复用前置，按功能清单的硬依赖排出**59项无循环、依赖先于使用者**的顺序，可依次交给开发对话。

这不是承诺59项均可在缺少SDK/设备时独立验收通过。每项开工前看对应策划的当前证据与未知；平台条件缺失就如实登记未验，继续做不依赖该未完成部分的本地功能。不要为通过而跳过前置、伪造SDK或把模拟记录当真机。

## 关键安排

- 第一个做F017持久化。已有真实单关可作为行为底座；F010/F011/F012的“收口”复用现有Model/Session/Controller及有界PASS，不是重写玩法。真实硬件取消限制保留到设备验证，不假称已测。
- F019钱包、F020结算、F008解锁完成后，已有玩法才形成可保存且可累计奖励的主线；F015补星级来源，F016补真实提示。
- F023～F028做建设与三园，再以F048真实事件验证120→80→160→120；不先做自动送钱的引导样片。
- F041先给真实任务事件与领取服务，F035/F036再接蜂友跟随与亲密的实际消费侧。若任务篇要求的联动还没接入，该联动仍标待验，不提前记整功能完成。
- F052提供广告统一事务，再接5广告位与双端Adapter；F056等普通/限步/无尽基础结算齐后才验全覆盖。
- F051最终隐私基于实际SDK和发行主体，F063/F064必须用唯一Project实际产物与真实设备证据，不用源码DEBUG门禁替代包内审核。

## 每个功能的交付方式

1. 阅读独立策划及其前置，限定本次范围，保留已有未提交修改。
2. 复用正式Prefab、typed Inspector引用和唯一数据/奖励服务；动态几何或列表实例可生成，固定页面不能运行时补整树。
3. 规则、写失败回滚、重复提交、异步迟到与生命周期用定向验证证明。
4. 按影响范围运行当前回归、TypeScript、资源审核与真实Creator操作，附当次指纹和报告；需要平台的项目单独列未验。
5. 美术与交互达标后更新[功能完成目录](功能完成目录.md)，登记实际完成日期和证据，不自动把相邻功能标完成。
