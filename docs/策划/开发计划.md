## 2. RALPLAN-DR：原则、驱动与方案

**五条原则**：①先保存成功再发布成功表现；②复用当前可用实现与已交付原稿；③一次一个功能，每项可验收且可追踪；④硬依赖先于消费者，跨功能软联动另设闸门；⑤Creator、模拟平台和真实设备证据分开，缺条件如实未验。

**三个决策驱动**：玩家资产与旧档不能损坏；用户需要能逐个执行的稳定任务顺序；当前已有框架和单关，应尽快形成可保存的真实主线，而非长时间搭建另一个体系。

| 可行方案 | 收益 | 代价、适用边界 |
| --- | --- | --- |
| A：保留既有59顺序，增加7个阶段与联动闸门（选择） | 不打乱已交接功能的硬依赖；F017先建立唯一写入边界；每一功能有独立交付记录，适合单人逐项推进。 | GM完整工具较晚；前期要写定向测试fixture，F041等必须在后置消费者接入后再复验联动，阶段不能仅按文件存在打勾。 |
| B：按体验竖切并前置最小GM，重排依赖无关项目 | 更早通过开发工具快速到达三园、活动与广告场景；多人可提前验证更完整体验。 | 需要重新发布顺序与拆分F060/F061完成边界；存档schema、命令权限及恢复协议在早期频繁变化，单人上下文切换和临时GM清理成本更高。适合已确定多人并行和工具维护责任人的团队。 |

选择A是为了保持“一次一个功能”的稳定交接。吸收B的收益：早期建立只在测试中使用的确定性fixture与故障注入；它们不进入生产入口，不伪装GM，不把F060/F061提前标完成。共享协议冻结后允许只读审阅和独立Prefab接入准备并行，但完成与合入仍按原顺序。

## 3. 开工契约与关键路径

每个功能开工前读取对应独立策划、矩阵行及实际源码，列明本次拥有的脚本、Prefab、`.meta`、测试和接口。复验前置的实际证据；功能“基础已具备”只适用于其已证明范围，不等于它后续承担的新业务接入已经完成。

区分两个出口：**本地候选通过**表示明确列出的规则/事务/Creator范围已有当前证据，可以交给不依赖缺口的后续工作；**整项完成**必须关闭该功能所要求的全部平台/设备与联动项目，才可更新完成目录。下文阶段退出以所列范围为界，真实硬件取消或真实SDK缺条件时保留未验、不得升级整项状态。后续功能只有在其实际使用的前置范围已验证、接口已冻结时才能进入；不能以F064总验收为由拖延每项自身必需的Creator和设备检查。

默认关键路径为：**F017 → F019 → F020 → F008 → F023 → F026/F027 → F029/F030/F034 → F041/F035/F036 → F052及5广告位 → F058/F059 → F063 → F064**。这是集成重点，不替代矩阵中的全部硬依赖；F022在周期消费者之前、F018在真实旧档接入之前，F046/F047和F048/F049按矩阵插入。

### 3.1 唯一事务边界

F017先冻结版本信封、profile/revision、存储端口、完整快照提交与备份/恢复协议；具体字段/API由该功能落实。F019只在该候选快照内计算余额，F020统一稳定题ID/attempt/run/settlement/claim幂等键。业务Controller发命令，领域服务计算，唯一提交器串行或版本比较，UI只显示已提交结果。[F017策划](功能/F017_持久化玩家存档与写失败回滚.md)和[F020策划](功能/F020_首通奖励与统一幂等结算.md)是合同来源，不能在各功能另建localStorage或奖励Manager。

统一命令流程：读取已提交快照 → 校验权限、身份和预期版本 → 生成含余额/进度/领取键/业务事件的候选 → 故障可恢复的完整提交 → 发布新快照与唯一事件 → 刷新UI/动效。失败不发布“到账”，重复命令返回既有回执；消费者按事件ID去重，不能靠“页面只打开一次”幂等。

领域事件生产者是完成、建设、无尽结算等服务；F022仅提供日周键与时间合同，不分发或累计建设/任务业务。F023的建设事件、首建照片来源记录应在升级事务保留，即使相册UI到F039才接入。后装消费者的回放范围必须明确：历史持有可由已提交来源派生，历史奖励不得补发，迁移不得伪造新完成事件。不得为了补齐日任务把所有历史完成算作今天。

### 3.2 旧档先保护，再接入

F018排在P01后半段，不允许因此在F017阶段把未知/旧版本档当新玩家覆盖。F017启动探测遇到旧schema、未知格式或损坏档时保留原字节与备份、阻断写入，提供明确恢复/待迁移反馈；前期只用显式隔离的新测试档进行开发。**任何真实旧档启用、升级安装验证或旧广告回执重放，都必须等待F018门禁通过**。读取与备份可以早做；实际兼容映射、迁移整体提交、二次迁移等价、旧限步17–30保留身份由[F018](功能/F018_旧档迁移与稳定身份兼容.md)负责。不存在样本的历史格式登记未知，不能口头宣称全兼容。

### 3.3 Prefab和资源接入

复用当前80个正式模板与2个DEBUG模板的绑定结构，每个本功能页面交付真实业务使用点、组件、Prefab/`.meta`和有效事件引用。固定UI不运行时搭完整树；动态棋盘、粒子、列表可见实例按约束生成。core不导入`cc`、浏览器全局或业务入口，Controller与公共组件之间传窄接口。

列表独立组件与item Prefab；长列表可见区加缓冲复用，固定少量可Layout，不能让Layout与虚拟算法共同控制同一content。显示订阅、隐藏解除，销毁取消请求并先销毁实例再释放所属scope；异步返回检查view、数据身份与请求代次。资源`addRef/decRef`对称，不用`releaseAll`清别页。若实际复制BigHero纯TS，再建立来源/目标哈希manifest；本计划不宣称已复制。

## 7. 一次一个功能的交付节奏

1. **入场核对**：读独立策划、矩阵及真实前置，指定本功能拥有的文件、可改接口与风险；记录当前源身份和既有失败。涉及D项先按冻结点处理，不把全部问题集中到末尾。
2. **先验证规则再接UI**：以真实业务反例、故障注入和幂等测试固定新增契约，复用现有领域能力；不要为低影响文案改动编写镜像实现的测试。
3. **接唯一数据与正式Prefab**：Controller/服务与当前装配层对接；typed引用、事件、资源所有权、加载失败和关闭后迟到一起完成，保留现有未提交修改。
4. **按范围验证**：运行定向测试，以及当前`npm test`、`npm run typecheck`、`npm run audit`；有UI改动做实际Creator导入/实例化/操作与原稿对照，平台功能加真实SDK设备检查。现有入口见[package.json 第8行](../../package.json#L8)，各native验证脚本范围先读再运行，脚本通过不能外推未覆盖业务。
5. **登记与交接**：只有本功能必需范围和相关闸门通过，才更新功能完成目录的日期、源码/包/证据链接；缺外部条件记待验范围，不能用“代码已写”标整项完成。列出交给下一功能的接口/事件和未关闭联动，不自动把相邻项标完成。

一个功能可拆规则、事务、Prefab接入和验收子任务，但对用户仍保持一个F号，不另造第二套策划。P00完成后先试行F017/F019/F020的交付模板，记录实际投入、返工和验证时间，再校准其余任务的相对工作量。没有实际人员与速度数据时不承诺总周数/人日。

## 11. ADR：为什么保留原顺序并增加门禁

**Decision**：采用方案A，保留59项顺序，以P00基础复验及P01–P06分阶段推进；所有65项进入矩阵，以唯一存档/结算/业务事件事务和额外联动门禁贯穿。

**Drivers**：保护旧档与玩家权益；满足一次一个功能交接；复用当前框架/单关并尽快形成可保存闭环。

**Alternatives considered**：方案B的竖切/最小GM前置可以加快复杂场景到达，但需要重排交接与长期维护早期命令权限；本项目目前优先稳定顺序和单写入责任，不采用该重排。

**Why chosen**：A直接复用已经无循环的依赖表，解决缺少阶段退出、事务联动和真实平台验证的问题；通过测试fixture得到早期验证能力，无需创建一套临时生产GM。

**Consequences**：GM正式功能较晚；F041、相册等需要后置联动复验；平台外部阻塞必须显式保留，无法靠本地代码完成宣告全产品完成。交换来的是稳定任务编号/顺序和清晰数据所有权。

**Follow-ups**：开工先复验P00、再交付F017；在相应冻结点解决D项，F036回归G-TASK-AFFINITY，F063/F064以真实包关闭平台/性能门禁。任务矩阵和验收计划随批准的范围变更更新，功能完成目录只在真实完成后更新。
